# 02. 락 없는 발급 로직의 경쟁 상태 재현

## 문제

순차 요청에서 맞는 로직이 동시 요청에서도 맞는지 확인한 적이 없었다. 선착순 쿠폰은 오픈 순간 요청이 동시에 몰리므로, 해결책을 고르기 전에 무엇이 어떻게 깨지는지 먼저 눈으로 확인한다.

## 요구사항 (이번 범위)

- 순진한 check-then-act 발급 로직: 중복 확인(EXISTS) → 재고 확인(SELECT) → `issued_quantity`를 읽은 값 + 1로 UPDATE → INSERT.
- 응답: 성공 201, 중복 409 `{"code": "ALREADY_ISSUED"}`, 재고 소진 409 `{"code": "SOLD_OUT"}`. 중복 확인을 재고 확인보다 먼저 한다.
- 락·제약은 일부러 두지 않는다 (`main.py`에 주석으로 의도 표시).

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 재현 방식 | pytest 동시성 테스트 (`asyncio.gather` + `client` fixture) | 요청마다 별도 커넥션·트랜잭션이 생겨 실제 경쟁이 일어난다 (TRUNCATE 격리 덕분). 재현 테스트가 문제 4·5의 스펙으로 남는다. 실험 스크립트는 자동 확인 장치가 남지 않고, k6는 문제 3의 일 |
| 테스트 순서 | 순차 테스트로 로직을 먼저 만들고 동시 테스트로 깨뜨림 | 로직이 없는 상태의 동시 테스트 실패는 경쟁 상태의 증거가 아니다. 순차로 맞다는 것을 증명해야 동시 실패의 원인이 "틈" 하나로 좁혀진다 |
| 개념 분리 | 테스트마다 원인이 하나만 남게 조건 설계 | 갱신 손실: 재고 1000으로 초과 발급 불가능하게. 중복 발급: 재고 100 + 같은 user. 초과 발급: 서로 다른 user |
| 검증 방식 | 불변식 (`발급 수 == 재고`, `카운터 == 발급 수`, `user당 1장`) | 동시성 결과는 비결정적이라 특정 숫자가 아니라 항상 지켜져야 할 규칙을 검사한다. `<=`가 아니라 `==`로 과소 발급도 잡는다 |
| 알려진 버그 표시 | `xfail(strict=True, raises=AssertionError)` | 고쳐지면 XPASS로 실패해 표시 제거를 강제한다. `raises`가 없으면 setup 에러도 xfail로 숨는다 |
| async 마커 | 모듈 단위 `pytestmark = pytest.mark.anyio` | 테스트마다 붙이다 빠뜨리는 실수 방지 |

## 측정 결과

조건: 로컬 Docker, 앱은 ASGITransport(한 프로세스, asyncio), 테스트 엔진 풀 기본값 (`pool_size=5`, `max_overflow=10`), Postgres 18 기본 격리 수준 READ COMMITTED. 실행마다 값이 달라지므로 범위로 기록한다.

| 현상 | 조건 | 기대 | 결과 (관측 범위) |
|---|---|---|---|
| 초과 발급 | 재고 10, 서로 다른 user 100명 동시 | 10장 | 96~100장 |
| 갱신 손실 | 재고 1000, 서로 다른 user 100명 동시 | 카운터 100 | 카운터 4~9 |
| 중복 발급 | 재고 100, 같은 user 10회 동시 | 1장 | 4~10장 |

## 원인

읽기와 쓰기 사이의 틈. 각 요청이 SELECT로 읽은 값을 근거로 판단하는 동안 다른 요청이 커밋하면 그 근거가 낡는다.

- READ COMMITTED에서 SELECT는 다른 트랜잭션의 행 락을 기다리지 않고 마지막 커밋 값을 읽는다. 그래서 모두가 같은 옛 값을 본다.
- `values(issued_quantity=issued_quantity + 1)`은 Python 값(읽은 시점의 숫자)을 상수로 보낸다. UPDATE끼리는 행 락으로 줄을 서지만 각자 옛 값 + 1로 덮어쓴다. 컬럼 표현식 `coupon.c.issued_quantity + 1`이면 갱신 손실은 사라지지만 판단(`if`)이 여전히 낡은 값이라 초과 발급은 남는다.
- EXISTS → INSERT도 같은 check-then-act라 같은 user의 동시 요청이 모두 "아직 안 받음"을 본다.

## 알게 된 함정

- async 테스트에 `@pytest.mark.anyio`가 빠지면 fixture setup 에러가 나는데, xfail이 이를 "예상된 실패"로 숨겼다. 다음 테스트의 fixture 정리까지 꼬여 엉뚱한 테스트에서 ERROR가 났다. red를 확인한 뒤에 xfail을 붙이고, `raises`로 기대 예외를 한정한다. `pytest --runxfail`로 실제 실패 이유를 확인할 수 있다.
- `.scalar_one()`은 첫 번째 컬럼만 돌려준다. `returning(coupon)`에 써도 에러 없이 id만 나온다. 원하는 컬럼을 명시한다.
