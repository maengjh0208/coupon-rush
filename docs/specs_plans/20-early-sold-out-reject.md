# 20. app CPU 상한: 매진이면 DB 전에 거절

## 문제

재고를 Redis로 옮긴 뒤(07) 처리량 상한을 다시 app CPU가 정했다. 2워커 / `cpus: 2`에서 app CPU 200% 포화, postgres는 여유가 있었고, 요청당 app CPU는 약 1.4ms였다. 실제 선착순은 수량 << 요청이라 대부분이 거절될 요청이다. 그런데 거절될 요청도 DB SELECT 두 번(쿠폰 확인, 중복 확인)과 BEGIN/ROLLBACK을 다 치른 뒤에야 `DECR`에서 SOLD_OUT을 받았다.

## 확인: 프로파일 (11-25)

조건: bench compose (app 워커 2 / `cpus: 2` / 512m, postgres `cpus: 2` / 1g, redis `cpus: 1` / 256m), 코드 `869907a`, 수량 1000, RATE 2000, 30초 1회. py-spy를 별도 컨테이너(`--pid=container:<app>`, `SYS_PTRACE`)에서 붙여 워커 1개를 20초, 100Hz로 샘플링했다 (샘플 1584, 실패 417). 프로파일러를 붙인 상태라 처리량(1539)은 비교에 쓰지 않는다.

| 비중 | 어디서 |
|---|---|
| **37.9%** | DB 클라이언트 (SQLAlchemy + asyncpg): SELECT 2번, BEGIN/ROLLBACK, 캐시 키 생성(4.7%), greenlet 전환, 결과 처리 |
| 26.1% | FastAPI / Starlette |
| 24.9% | 이벤트 루프와 네이티브 코드 (uvloop, C, 식별 안 됨) |
| 8.1% | redis-py |
| 3.0% | uvicorn / httptools |

요청의 98%가 SOLD_OUT인데 CPU의 약 38%를 결과에 영향이 없는 DB 작업에 썼다. 나머지 약 50%(프레임워크, 이벤트 루프)는 모든 요청이 내는 고정 비용이다.

## 선택지

| | 방식 | 판단 |
|---|---|---|
| A | DB 조회 전에 `GET stock`, 0 이하면 바로 SOLD_OUT. 키가 없거나 남아 있으면 지금 흐름 그대로 | **선택**. 가장 작은 변경이다. GET은 키를 만들지 않아 #19와 충돌하지 않는다. 최종 판단은 여전히 `DECR`라 GET이 오래된 값을 봐도 정합성이 깨지지 않는다 |
| B | Lua로 "키가 있을 때만 DECR"하고 DECR을 맨 앞으로 이동 | 왕복 1번으로 끝난다. 대신 Lua를 새로 도입하고, 중복 확인이 DECR 뒤로 밀려 중복 요청도 차감 후 보상 INCR을 해야 한다 |
| C | 워커 메모리에 매진 플래그 | I/O가 0이다. 보상 INCR로 재고가 되살아나도 플래그가 남아 덜 발급되므로 무효화 설계가 필요하다. A로 부족할 때 얹는다 |

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| GET 위치 | 첫 번째 SELECT **앞** | SQLAlchemy asyncpg 어댑터는 트랜잭션을 첫 쿼리에서 연다. SELECT ① 뒤에 두면 거절될 요청이 BEGIN, SELECT, ROLLBACK을 여전히 한다 (4번 → 3번). 앞에 두면 0번이다 |
| 없는 쿠폰 | 키가 없으면(`None`) 통과시켜 DB가 404를 판단 | "GET을 먼저 하면 없는 쿠폰이 SOLD_OUT이 된다"는 걱정은 맞지 않는다. #19 이후로 없는 쿠폰에는 재고 키가 생기지 않는다. `int(None)`을 막으려면 `None` 확인이 먼저다 |
| 거절 조건 | `<= 0` | 경합 중 DECR이 재고를 잠깐 -1로 만들었다가 보상 INCR로 되돌리는 순간이 있다 |
| 응답 우선순위 | 매진 뒤 중복 요청은 `SOLD_OUT` (전에는 `ALREADY_ISSUED`) | 매진 뒤에는 어느 쪽이든 받을 수 없다는 결과가 같다. 시작 전인데 재고 0인 쿠폰도 `NOT_STARTED` 대신 `SOLD_OUT`이 되지만 정상적으로는 생기지 않는다 |
| 키 유실 시 재고 다시 채우기 | 이번에 하지 않음 → 문제 23 | 성능 문제와 정합성 문제를 섞으면 측정 결과를 해석할 수 없다. 동시 SET(`NX` 필요), 진행 중 트랜잭션 반영, 요청 경로 vs 별도 복구 작업을 따로 정해야 한다 |

## 진행

1. red: `test_returns_sold_out_when_stock_exhausted_even_if_already_issued`. 수량 1로 사용자 1이 받은 뒤 같은 사용자가 다시 요청하면 SOLD_OUT. 순서 자체는 응답으로 보이지 않지만, 두 확인이 동시에 걸리는 상황을 만들면 우선순위가 응답 코드로 드러난다. 두 응답 모두 409라 status 검사는 넣지 않았다. `{'code': 'ALREADY_ISSUED'} == {'code': 'SOLD_OUT'}`로 실패하는 것을 확인했다.
2. green 첫 시도: GET을 SELECT ① 뒤에 두었다 (없는 쿠폰이 SOLD_OUT이 될까 봐). 테스트는 통과했지만 거절 경로의 DB 작업이 대부분 남아서 SELECT ① 앞으로 옮겼다. `test_returns_not_found_when_coupon_does_not_exist`가 없는 쿠폰 경로를 지킨다.
3. 리뷰: 옮기면서 중복 확인 블록의 주석이 지워져서 되살렸다. GET 블록에도 "빠른 거절용, 최종 판단은 DECR" 주석을 달았다.

## 측정 (11-26, 같은 날 변경 전 → 후 순서)

조건: 위 프로파일과 같은 bench compose, 풀 5+10, k6 `constant-arrival-rate` 30s, `preAllocatedVUs=500`, `maxVUs=1000`, 수량 1000, 3회. CPU는 측정하지 않았다.

|---|---|---|---|---|---|---|
| 변경 전 `869907a` | 2000 | `20261126-142831-869907a` | 1935 (1920~1950) | 23~30ms | 0.80~1.1s | 약 1460 |
| 변경 후 `236f729` | 2000 | `20261126-143240-236f729` | 1948 (1900~1975) | 0.74ms, 0.76ms, 13.9ms | 0.25~1.09s | 800~2752 |
| 변경 전 `869907a` | 3000 | `20261126-143735-869907a` | **1793 (1767~1817)** | 451~526ms | 1.58~1.64s | 약 35000 |
| 변경 후 `236f729` | 3000 | `20261126-143951-236f729` | **2381 (2312~2431)** | 20~21ms | 2.34~2.41s | 17000~20000 |

모든 회차에서 발급 1000, Redis 재고 0이었다.

## 결과

- **포화 처리량이 약 1790에서 약 2380 req/s로 올랐다 (약 +33%, 같은 날 상대 비교).** RATE 2000은 두 버전 모두 보낸 양을 거의 다 처리해서 차이가 드러나지 않았고, RATE 3000에서 둘 다 포화됐다.
- **RATE 3000에서는 VU 1000이 바닥났다.** 리틀의 법칙으로 평균 지연 × 처리량이 변경 전 0.55s × 1793 ≈ 985, 변경 후 0.41s × 2381 ≈ 975로 둘 다 `maxVUs`에 붙었다. 서버가 따라가지 못해 줄이 길어진 결과이므로(07과 같은 판단) 처리량은 서버 상한으로 본다. 다만 CPU를 측정하지 않아서 상한을 app CPU가 정하는지는 확인하지 않았다.
- **변경 후 지연은 양극화됐다.** RATE 3000에서 p50은 약 21ms인데 p95 2.4s, max 14~18s다. 대부분은 GET 한 번으로 바로 끝나고, 일부가 오래 기다린다. 원인은 확인하지 않았다.
- 변경 전 RATE 3000(1793)이 RATE 2000(1935)보다 낮다. 과부하에서 처리량이 오히려 떨어지는 모양이지만 1조건 3회라 결론 내지 않는다.
- 남은 CPU의 약 절반은 프레임워크와 이벤트 루프의 고정 비용이다. 더 올리려면 C(메모리 플래그)로 Redis 왕복까지 없애거나 인스턴스를 늘린다. app은 상태가 없어서 실무에서는 인스턴스 추가가 먼저다.

## 알게 된 것

- 선착순 시스템의 처리량은 거절을 얼마나 싸게 하느냐로 정해진다. 확인은 싼 것부터 한다(fail fast). 빠른 거절과 최종 판단을 나누면, 빠른 거절이 오래된 값을 봐도 정합성은 최종 판단이 지킨다 (중복은 EXISTS와 UNIQUE, 재고는 GET과 DECR).
- 순서처럼 응답에 직접 보이지 않는 성질은 두 조건이 동시에 걸리는 상황을 만들면 테스트할 수 있다.
- SQLAlchemy asyncpg 어댑터는 `engine.begin()`에서 BEGIN을 보내지 않고 첫 쿼리에서 보낸다. 쿼리 없이 끝나면 BEGIN과 ROLLBACK도 없다. 그래서 의존성으로 커넥션을 받아 두더라도, 쿼리 전에 거절하면 DB 왕복은 0번이다 (커넥션 풀 체크아웃은 일어난다).
- 보내는 양이 상한보다 낮으면 처리량은 보낸 양에 묶인다. 처리량 개선은 두 버전이 모두 포화되는 RATE에서 비교한다.
- py-spy는 이미지를 바꾸지 않고 `--pid=container:<id> --cap-add SYS_PTRACE`로 붙일 수 있다. greenlet(SQLAlchemy async) 안의 샘플은 코루틴 스택이 끊겨서 함수별로는 나눌 수 없었고, 라이브러리별로 묶어서 봤다.
