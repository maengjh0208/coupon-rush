# 06. 락 보유 시간: FOR UPDATE를 조건부 UPDATE로 대체

## 문제

FOR UPDATE 방식은 쿠폰 row 락을 쥔 채 왕복 3번(SELECT FOR UPDATE → UPDATE → INSERT)과 COMMIT을 한다. 모든 요청이 같은 row에 몰리므로 락 보유 시간이 직렬 구간이 되고, 이론상 처리량 상한을 정한다 ([04](04-over-issue-for-update.md), [05](05-duplicate-issue-unique.md)).

## 요구사항 (이번 범위)

- 정합성은 그대로: 발급 수 <= 재고, `issued_quantity` == 발급 row 수, (coupon, user)당 1장.
- 응답도 그대로: 201 / 404 `COUPON_NOT_FOUND` / 409 `SOLD_OUT`, `ALREADY_ISSUED`.
- 락을 쥔 구간의 왕복 수를 줄인다.

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 진행 방식 | FOR UPDATE를 **대체**한다. `ISSUE_STRATEGY`로 나란히 두지 않음 | 방식을 하나씩 더 나은 것으로 바꾸고, 이전 방식은 커밋 해시로 재현한다 (PROJECT.md "동시성 방식의 발전"). 전환 스위치는 지금 쓸 데가 없는 추상화다 |
| 재고 차감 | `UPDATE coupon SET issued_quantity = issued_quantity + 1 WHERE id = :id AND issued_quantity < total_quantity` | 확인과 쓰기가 한 문장 안에서 원자적이다. 판단(`if`)이 앱에서 DB의 WHERE로 옮겨가 read-judge-write의 틈이 없다. 행 락은 여전히 잡지만, 락을 쥔 구간이 UPDATE → INSERT → COMMIT으로 왕복 하나가 줄어든다 |
| `rowcount == 0`의 의미 구분 | 0이면 쿠폰 EXISTS를 한 번 더 조회해서 SOLD_OUT / CouponNotFound를 고른다 | 0은 "매진"과 "없는 쿠폰" 두 가지다. 추가 조회는 거절 경로에서만 일어나므로 성공 경로 비용은 늘지 않는다. 문제 14의 404 테스트가 이 모호함을 잡는다 |
| 테스트 | 새 테스트 없음, 기존 9개를 스펙으로 사용 | 동작(응답, 정합성)은 바뀌지 않고 구현만 바뀐다. 리팩터와 같은 위치 |

## 진행 과정

1. FOR UPDATE + `if` 판단을 조건부 UPDATE + `rowcount` 확인으로 교체.
2. 처음 구현에서 WHERE의 부등호가 반대였다 (`total_quantity < issued_quantity`). 정상 상태에서 항상 거짓이라 모든 요청이 SOLD_OUT이 된다. 기존 201 테스트가 잡았다.
3. 수정 후 pytest 9 passed.

## 확인한 것

**PyCharm이 `if result.rowcount == 0:` 블록을 회색(도달 불가)으로 표시했다. 오탐이다.** `CursorResult.rowcount`는 `@util.memoized_property`이고, 타입 체크 시점에는 `generic_fn_descriptor`다. 이 디스크립터의 `__get__` 오버로드는 인스턴스 접근이면 `int`를 돌려주는데, IDE가 디스크립터 자신을 돌려주는 오버로드로 추론하면 "디스크립터 == 0은 항상 거짓"이 되어 블록을 죽은 코드로 본다. SOLD_OUT 테스트와 404 테스트가 그 블록을 지나야만 통과하므로, 실제로 실행된다는 것은 테스트가 증명한다. IDE 표시는 정적 추론이지 사실이 아니다.

## 측정

### 조건

- 06 커밋 `a330daf`, 05 커밋 `e8363c4`
- 나머지 조건은 [03](03-load-test-environment.md)과 같다: app `cpus: 1` / 512m / 워커 1, postgres `cpus: 2` / 1g / READ COMMITTED, 풀 `pool_size=5` + `max_overflow=10`, k6 `constant-arrival-rate` 30s, `preAllocatedVUs=500`, `maxVUs=1000`, 재고 100000, 조건마다 3회
- CPU는 측정 중 `docker stats`를 눈으로 본 대략값 (기록 아님)

### 같은 날 번갈아 측정 (2026-11-06, 포화 구간, 중앙값과 3회 범위)

| 시각 | 코드 | 결과 폴더 | RATE 700 처리량 | RATE 1000 처리량 | app / postgres CPU |
|---|---|---|---|---|---|
| 16:03 | 06 (커밋 전, 아래 함정 참고) | `20261106-160332-67cf19f` | 551 (523~555) | 546 (518~548) | 90% / 확인 안 함 |
| 16:21 | 05 | `20261106-162113-e8363c4` | 627 (583~635) | 612 (609~613) | 90%+ / 40%+ |
| 16:28 | 06 | `20261106-162814-a330daf` | 577 (564~629) | 608 (564~612) | 90~95% / 40% |

- 모든 실행에서 HTTP 실패 0%, 발급 row 수 == `issued_quantity`.
- 포화 구간 p50은 1~1.7s다. VU가 `maxVUs` 1000개까지 묶인 상태라 리틀의 법칙으로 지연 ≈ 1000 / 처리량 ≈ 1.6~1.8s가 된다. 서버 성능이 아니라 k6 설정과 처리량으로 정해진 값이라 비교 지표로 쓰지 않는다.

### 해석

- **05와 06은 오차 범위 안에서 같다.** RATE 1000에서 612 vs 608이고, RATE 700은 범위가 겹친다(583~635 vs 564~629). 같은 06 코드가 16:03에는 546, 16:28에는 608로 측정 순서만으로 약 11% 차이가 났다. 첫 비교에서 보인 "06이 20% 느리다"는 측정 시점 차이였다.
- **락 보유 시간이 상한이라는 문제 6의 전제는 지금 구성에서 관찰되지 않는다.** app CPU가 먼저 90~95%로 포화되고, postgres는 40% 근처에서 여유가 있다. 병목이 app인 동안에는 DB 쪽 직렬 구간을 줄여도 처리량이 오르지 않는다. 문제 5 때 예상한 결과와 같다.
- **그래도 조건부 UPDATE를 유지한다.** 정합성 규칙(재고 확인과 차감)이 앱의 `if`가 아니라 SQL 한 문장에 있고, 쿼리가 하나 줄었다. 성능 이득은 병목이 DB로 옮겨간 뒤에 다시 측정한다.
- **어제(2026-11-05)와 오늘 측정은 비교할 수 없다.** 같은 05 코드가 RATE 1000에서 708 → 612로 떨어졌다. 문제 18로 분리했다.
- 저부하(RATE 100~500)는 06을 16:03에 한 번만 측정했다. RATE 100 p99가 3회 모두 15~19ms로 안정적이었지만 비교할 같은 날 05 측정이 없어서 해석하지 않는다 (문제 16).

## 알게 된 함정

- **조건부 UPDATE도 락을 잡는다.** UPDATE는 대상 row에 행 락을 잡고 COMMIT까지 유지한다. 락이 사라지는 것이 아니라 락을 쥔 구간이 짧아지는 것이다. READ COMMITTED에서 락을 기다리던 UPDATE는 락이 풀리면 최신 row로 WHERE를 다시 평가하므로, 앞 트랜잭션이 마지막 재고를 가져갔으면 0 rows가 된다.
- **측정 전에 커밋한다.** 첫 06 측정은 커밋 전에 돌려서 결과 폴더 이름이 이전 커밋(`67cf19f`)이 됐다. volume mount 덕분에 실제로는 새 코드가 측정됐지만, 폴더 이름만으로는 알 수 없다.
- **비교는 같은 시간대에 번갈아 측정한다.** 다른 시각에 측정한 결과는 코드 차이와 환경 차이가 섞인다. A → B → A 순서로 돌리면 시간에 따른 변화가 드러난다.
