# 03. 조건이 고정된 부하 테스트 환경

## 문제

측정 조건(CPU, `--reload`, DB 상태, 부하 모양)이 고정되지 않으면 측정값의 차이가 방식에서 왔는지 환경에서 왔는지 구분할 수 없다. 문제 4부터 방식 간 비교를 하려면 고정된 측정 환경과 기준선(락 없는 현재 버전)이 먼저 필요하다.

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 개발/측정 환경 분리 | `docker-compose.bench.yaml` override (`-f`로 병합) | 개발 환경(`--reload`, 제한 없음)은 그대로 두고 측정 조건을 파일 하나에 모은다. 파일 자체가 조건 기록 |
| 부하 모델 | 열린 모델 `constant-arrival-rate` | 닫힌 모델(VU 고정)은 서버가 느려지면 부하가 저절로 줄어 지연이 측정에서 빠진다 (coordinated omission). 선착순 사용자는 남의 응답을 기다리지 않는다 |
| 재고 대비 요청 | 재고(100000) ≥ 총 요청 | 모든 요청이 쓰기 경로(쿠폰 row UPDATE)를 지나 hot row 경합 비용을 잰다. 재고가 작으면 대부분 SOLD_OUT(읽기만) 경로를 재게 된다 |
| user_id | `exec.scenario.iterationInTest` | 요청마다 고유 사용자. ALREADY_ISSUED 경로가 섞이지 않게 |
| VU | `preAllocatedVUs: 500`, `maxVUs: 1000` | 측정 중 VU 생성(CPU 사용, 생성 지연에 따른 drop)이 측정을 오염시키지 않게. `vus_max`가 측정 내내 500이면 생성 없음 |
| keep-alive | uvicorn `--timeout-keep-alive 30` | VU 500개에 RATE 100이면 VU당 유휴 약 5초로 uvicorn 기본 5초와 겹쳐 EOF 실패(약 1%). 서버 keep-alive는 클라이언트 유휴 시간보다 길어야 한다 |
| 반복 | 조건마다 3회, 중앙값 + 범위 기록 | 꼬리 지연은 실행마다 크게 흔들린다. 평균은 튀는 1회에 끌려간다 |
| 실행 절차 | `scripts/bench.sh` (reset → k6 → 정합성 SQL, 결과는 `bench-results/<시각>-<커밋>/`) | reset 누락과 결과 전사 실수 방지. 결과를 코드 버전과 묶는다 |
| 병목 위치 | 지금 조건 유지 (app CPU 병목) | 측정 중 app CPU 80~90% / 100%, postgres 60~70% / 200%. 문제 4에서 방식별 상한과 `docker stats`를 보고, 상한이 앱에 가려지면 앱 용량을 늘린다 |

## 측정 조건

- 커밋 `2d5fc77`, 결과 `bench-results/20261028-164634-2d5fc77/`
- 호스트: Mac, CPU 8개. Docker VM CPU 8개 / 메모리 4GB. k6는 호스트에서 실행 (같은 CPU 공유)
- app: `cpus: 1`, `mem_limit: 512m`, uvicorn 워커 1개, `--reload` 없음, `--timeout-keep-alive 30`
- postgres 18: `cpus: 2`, `mem_limit: 1g`, 기본 설정 (READ COMMITTED)
- SQLAlchemy 엔진 기본 풀: `pool_size=5`, `max_overflow=10`
- k6: `constant-arrival-rate`, 30s, `preAllocatedVUs=500`, `maxVUs=1000`
- 실행 전 `reset_db.py 100000`, 실행 사이 5초 대기, 조건마다 3회

## 기준선: 락 없음 (중앙값, 괄호는 3회 범위)

| RATE | 처리량 (req/s) | p50 | p95 | p99 | max | dropped | 갱신 손실 |
|---|---|---|---|---|---|---|---|
| 100 | 100 | 3.05ms | 7.11ms (5.8~7.8) | 20.2ms (13~28) | 88ms | 0 | 1.4% (0.9~2.2) |
| 300 | 300 | 1.90ms | 11.1ms (10.6~12.4) | 125ms (105~139) | 264ms | 0 | 7.1% (7.0~7.2) |
| 500 | 500 | 1.61ms | 32.7ms (21.5~46.5) | 128ms (68~135) | 320ms | 0 | 12.8% (11.4~14.1) |
| 700 | 700 | 2.37ms | 73.2ms (62~252) | 217ms (165~504) | 542ms | 0 | 35.7% (33.0~43.0) |
| 1000 | **729 (518~794)** | 1.19s | 2.10s (2.0~3.6) | 3.02s (2.4~5.0) | 5.4s | 7482 (5465~13030) | 92.7% |

- 모든 실행에서 HTTP 실패 0%, 발급 row 수 = 처리된 요청 수 (재고 충분).
- 갱신 손실 = (발급 row − `issued_quantity`) ÷ 발급 row.

## 해석

- **포화점은 700~800 req/s 사이.** 700까지는 처리량이 도착률을 따라가고, 1000에서는 처리량이 도착률 아래로 떨어지고 VU 한도 도달로 drop이 생긴다.
- **지연은 절벽형.** 700에서 p50 2.4ms, 1000에서 1.19s. 처리 능력을 넘으면 지연의 대부분이 대기열 대기 시간이 된다.
- **과부하 구간은 측정이 불안정하다.** RATE 1000의 처리량이 실행마다 518~794로 흔들렸다 (이전 단독 실행은 866). 과부하에서는 처리량 자체가 떨어질 수 있으므로, 상한 비교는 포화 직전 구간(500~700)의 지연과 함께 본다.
- **꼬리는 포화 전부터 자란다.** 300에서 이미 p99가 p95의 10배. p95는 500부터, p50은 1000에서야 움직인다. 방식 비교에서는 p99를 우선 본다.
- **갱신 손실은 부하보다 빠르게 증가.** 1.4% → 7.1% → 12.8% → 35.7% → 92.7%. 동시에 처리 중인 요청이 많을수록 같은 옛 값을 읽는 트랜잭션이 늘어난다.
- RATE 100의 p50(3.05ms)이 300(1.90ms)보다 높다. 저부하에서 CPU가 유휴 상태로 내려갔다 깨어나는 비용 등으로 추정되나 확인하지 않았다.

## 한계와 이후 추가할 시나리오

- 재고 ≥ 요청이라 초과 발급은 부하 테스트에서 구조적으로 일어나지 않는다. 초과·중복 발급의 정합성은 pytest 동시성 테스트가 맡는다.
- 지금 병목은 app CPU. DB 방식 간 차이가 앱 상한에 가려지는지 문제 4에서 확인한다.
- 3단계(Redis): 재고 ≪ 요청 시나리오로 거절 경로 비교.
- 4단계(큐): `ramping-arrival-rate` 스파이크로 오픈 순간 재현.
