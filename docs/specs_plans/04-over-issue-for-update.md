# 04. 초과 발급: SELECT FOR UPDATE

## 문제

동시 요청에서 재고보다 많이 발급되고(재고 10에 96~100장), 카운터가 갱신 손실로 어긋났다(100건에 4~9). 원인은 재고를 읽고(SELECT) 판단하고(`if`) 쓰는(UPDATE) 사이의 틈이다 ([02](02-race-reproduction.md)).

## 요구사항 (이번 범위)

- 동시 요청에서도 발급 수 == 재고, `issued_quantity` == 발급 row 수.
- 중복 발급(문제 5)은 범위 밖. 중복 확인(EXISTS)은 락 밖에 그대로 둔다 (`main.py`에 주석으로 표시).

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 방식 | 재고 SELECT에 `.with_for_update()` (비관적 락) | 기존 check-then-act 구조를 그대로 두고 "읽기~커밋"을 직렬화한다. 락이 없는 버전과 한 줄 차이라 비용 비교가 깔끔하다 |
| 조건부 UPDATE (`WHERE issued < total`, `rowcount == 0`이면 SOLD_OUT) | 문제 6으로 미룸 | 락 보유 시간이 더 짧을 것으로 예상되는 2번째 방식. 구현체가 두 개가 되는 시점에 `ISSUE_STRATEGY`와 함께 도입 |
| 낙관적 락 (version 컬럼 + 재시도), SERIALIZABLE | 제외 | 모든 요청이 쿠폰 row 하나에 몰린다. 충돌이 드문 상황을 가정한 방식이라 hot row에서는 대부분 실패 후 재시도하고, 재시도가 다시 충돌하는 재시도 폭주가 된다 |
| 중복 발급을 같은 락으로 막기 | 하지 않음 | 아래 함정 참고. 문제 5에서 UNIQUE 제약으로 해결 |
| 테스트 | 기존 xfail 테스트를 스펙으로 사용 | 구현 후 XPASS(strict)로 실패해 표시 제거를 강제했다. 새 테스트 없이 red → green 확인 |

## 알게 된 함정

- **락은 락을 잡은 뒤의 읽기만 보호한다.** EXISTS를 FOR UPDATE 위에 두면 같은 user의 동시 요청이 모두 락 전에 "아직 안 받음"을 보고, 락 뒤에 줄을 서서 차례로 발급한다. 지금 중복 발급 테스트가 여전히 xfail인 이유.
- **EXISTS를 FOR UPDATE 아래로 옮기면 중복도 "우연히" 막힌다.** 하지만 그건 다음이 모두 성립할 때만이다: 문장 순서가 유지됨, 모든 발급 경로가 같은 쿠폰 row 락을 잡음, READ COMMITTED(문장마다 새 스냅샷이라 락 대기 후 EXISTS가 앞 트랜잭션의 커밋을 봄), 재고가 DB row에 있음. 3단계에서 재고를 Redis로 옮기면 이 락이 사라지고 중복 방지도 같이 사라진다. 규칙("user당 1장")은 규칙을 표현하는 수단(UNIQUE)으로 막는다.
- **FOR UPDATE 후 UPDATE의 `issued_quantity + 1`은 Python 값이어도 안전하다.** 락을 잡은 뒤 읽은 값이라 커밋 전까지 다른 트랜잭션이 바꿀 수 없다. 갱신 손실은 "읽은 값이 낡는 것"이 원인이었고, 락이 그 틈을 없앴다.

처리량이 bench 결과(546 / 430)와 다르다. 과부하 구간에서 실행마다 크게 흔들리는 것을 다시 확인했다.

## 해석

- **상한이 약 30% 낮아졌다.** 포화점이 700~800에서 500~550으로 내려왔다. 락이 쿠폰 row 하나에 대한 트랜잭션을 한 줄로 세우므로 처리량 상한 ≈ 1 ÷ 락 보유 시간. 546/s면 락 보유 약 1.8ms (SELECT FOR UPDATE ~ COMMIT 사이 왕복 3번 + 이벤트 루프 대기).
- **꼬리가 더 일찍 자란다.** 300에서 p99가 1.7배, 500에서 5.7배. 처리량은 아직 따라가도 락 대기열이 지연으로 먼저 나타난다.
- **과부하에서 처리량이 무너진다.** 1000에서 처리량이 700일 때보다 낮다(546 → 430). 많이 쌓일수록 일을 덜 한다.
- **app CPU는 기준선과 같이 한계 근처다.** 예상은 "락을 기다리느라 app CPU가 남는다"였지만 틀렸다. CPU는 같게 쓰는데 처리량은 줄었으므로, 줄어든 처리량만큼의 CPU가 다른 곳에 쓰인다.
- **가설 (확인 안 함): 두 병목이 서로를 키운다.** 락 때문에 쌓인 요청 수백 개도 앱 CPU를 쓴다 (연결 유지, 파싱, 커넥션 풀 대기열, 이벤트 루프 스케줄링). 앱 CPU가 바쁘면 락을 쥔 요청이 다음 쿼리를 보낼 차례를 늦게 받아 락 보유 시간이 늘고, 그만큼 더 쌓인다. 순수한 락 비용과 앱 CPU가 증폭시킨 비용이 섞여 있다.

## 한계와 남은 질문

- 지금 수치는 "app CPU 1개 조건에서의 FOR UPDATE 비용"이다. 락 자체의 비용과 앱 CPU 증폭을 분리하지 못했다.
- 문제 6에서 조건부 UPDATE까지 만든 뒤, 세 방식(락 없음 / FOR UPDATE / 조건부 UPDATE)을 앱 용량을 늘린 조건(예: `cpus: 2` + `--workers 2`)에서도 함께 재서 분리한다.
- 가설의 "쌓인 요청이 CPU를 어디에 쓰는가"는 프로파일러(py-spy 등)로만 확인 가능. 문제 12 영역.
- CPU 관측은 1회, 2초 간격 샘플이다. bench 스크립트가 CPU를 기록하지 않아 bench 실행과 같은 실행이 아니다.
