# 23. Redis 재고 키가 없으면 DB에서 다시 채움

## 문제

Redis 재고 키가 사라지면 그 쿠폰은 영원히 SOLD_OUT이 됐다. 키가 없을 때의 첫 요청에서 이런 일이 일어난다.

1. GET이 `None`이라 빠른 거절을 통과한다.
2. `DECR`이 없는 키를 0으로 보고 -1을 만들면서 키를 새로 만든다.
3. 보상 `INCR`이 0으로 되돌린다.

이후로는 키가 `"0"`이라 진짜 매진과 구분되지 않는다. 초과 발급은 없지만(fail closed) 판매가 멈춘다.

## 재현 (11-26)

dev compose, 수량 10.

| 순서 | 응답 | Redis 재고 |
|---|---|---|
| user 1 | 201 | 9 |
| `DEL coupon:1:stock` | | 키 없음 |
| user 2 | 409 SOLD_OUT | **0** |
| user 3, 4 | 409 SOLD_OUT | 0 |

DB는 `total_quantity=10`, `issued_quantity=1`이었다. 요청 하나로 잘못된 상태가 굳는다. 그래서 다시 채울 수 있는 시점은 **키가 없을 때, DECR이 키를 만들기 전**뿐이다.

## 실제로 키가 없어지는 경우

흔한 것부터 적었다. 빈도는 경험에 기댄 추정이다.

| 경우 | 예 |
|---|---|
| 처음부터 안 넣음 | 쿠폰 생성에서 DB INSERT는 성공하고 Redis SET이 실패함. 운영자가 DB에 직접 넣고 Redis 반영을 잊음 |
| 배포로 키 이름이 바뀜 | `redis_stock_key()` 형식을 바꾸면 모든 쿠폰의 키가 한꺼번에 "없음"이 된다 |
| 지속성 없는 재시작 | RDB·AOF를 끈 Redis, 볼륨 없는 컨테이너를 새로 만듦. 이 프로젝트도 redis에 볼륨이 없어서 `docker compose down` 후 `up`하면 키가 전부 사라진다 |
| eviction | 캐시와 같이 쓰는 Redis에 `allkeys-lru`. `volatile-*` 정책은 TTL 없는 재고 키를 지우지 않는다 |
| 실수 | DB 번호를 착각한 `FLUSHDB`, 패턴 `DEL`, `EXPIRE` |

SIGKILL 후 스냅샷 복구나 failover는 대부분 키가 남고 값이 과거로 돌아간다. 이건 문제 8이다.

## 선택지

| | 방식 | 판단 |
|---|---|---|
| A | 요청 경로에서 채움: GET이 `None`이고 DB가 쿠폰이 있다고 확인하면 `SET NX` 후 원래대로 DECR | **선택**. 키가 사라진 뒤 첫 요청에서 복구된다. "처음부터 안 넣음"과 "배포로 키 이름이 바뀜"도 같은 코드로 처리된다. 비용은 키가 없을 때 SET 1번뿐이다 |
| B | 별도 복구 작업(시작 시점이나 주기 작업) | 판매 중에 키가 사라지면 다음 실행까지 멈춘다. 스케줄러가 새로 필요하다 |
| C | Redis 설정으로 예방 (`noeviction`, AOF) | 원인 일부만 줄인다. FLUSH·failover를 못 막고 굳은 상태도 풀지 못한다. A와 함께 쓰는 보완책이다 |
| D | Redis가 0이면 DB로 다시 확인 | 거절될 요청이 다시 DB를 거친다. 문제 20에서 얻은 이득을 버린다 |

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 채우는 위치 | 쿠폰 존재·시작 확인 뒤, DECR 앞 | 존재 확인보다 앞이면 없는 쿠폰 id에도 키가 생긴다(문제 19). DECR보다 뒤면 이미 -1로 굳는다 |
| 채우는 값 | `total_quantity - issued_quantity` | 첫 SELECT에서 같은 row를 이미 읽으므로 쿼리가 늘지 않는다 |
| 계산 위치 | app (`row.total_quantity - row.issued_quantity`) | 행 하나의 정수 뺄셈이라 성능 차이가 없다. 원본 값이 보이고 도메인 규칙이 파이썬에 드러난다. `starts_at <= now()`는 DB에 남긴다 (시계 하나, 문제 15) |
| 계산식 이름 | `.label("started")` | 계산식은 `anon_1` 같은 익명 이름이 붙어 `row[2]`처럼 위치로 꺼내야 한다. 순서가 바뀌면 조용히 틀린다 |
| `SET` 옵션 | `nx=True` | 아래 |

### `NX`가 필요한 이유

키가 사라진 순간에는 동시 요청 여러 개가 함께 `None`을 본다. NX가 없으면 아래처럼 된다 (수량 10, 기존 발급 1).

| 순서 | 요청 A | 요청 B | Redis | 실제 |
|---|---|---|---|---|
| 1 | GET `None`, SELECT 9 | GET `None`, SELECT 9 | 없음 | 9 |
| 2 | `SET 9`, `DECR` → 8 | | 8 | 8 |
| 3 | | `SET 9` | **9** | 8 |

B가 A의 차감을 덮어쓴다. `None`을 본 요청이 N개면 최대 N장 어긋난다. B의 SELECT가 A의 COMMIT보다 앞이었다면 늦게 쓴 값이 더 오래된 값이다. NX면 첫 SET만 남고 이후 DECR이 지워지지 않는다.

NX가 없어도 초과 발급은 없다. Redis가 많다고 믿고 통과시킨 요청은 DB 조건부 UPDATE(문제 8)가 거절하고, 보상 INCR이 없어서 Redis가 스스로 맞춰진다. NX가 막는 건 정합성 사고가 아니라, 어긋난 만큼의 요청이 hot row까지 갔다가 거절되는 낭비다. 실행 순서에 따라 결과가 갈려 테스트로 만들면 flaky하므로, 테스트 대신 리뷰에서 확인했다.

## 남은 한계

- **GET과 DECR 사이의 틈.** GET이 값을 읽은 뒤 DECR 전에 키가 사라지면 DECR이 다시 -1을 만들고 같은 방식으로 굳는다. 아주 짧은 틈이라 이번에는 막지 않았다. 막으려면 "키가 있을 때만 DECR"하는 Lua 스크립트가 필요하다.
- **이미 `"0"`으로 굳은 상태는 A로 풀리지 않는다.** 진짜 매진과 구분되지 않는다. "Redis 재고 0인데 DB 발급 수 < 총수량"을 경보로 거는 모니터링이 잡을 영역이다(문제 12).
- **첫 SET의 값은 조금 클 수 있다.** SELECT 시점에 COMMIT되지 않은 발급은 빠져 있다. DB 최종 방어선이 흡수한다.

## 알게 된 것

- `DECR`·`INCR`은 없는 키를 0으로 보고 연산한 뒤 키를 만든다. 그래서 "재고 0에서 뺐다"와 "키가 없었다"가 같은 -1로 보인다. GET은 키를 만들지 않는다.
- 잘못된 상태가 정상 상태와 같은 모양으로 굳으면 다시는 감지할 수 없다. 복구는 신호(키 없음)가 살아 있을 때 해야 한다.
- 두 저장소에 나눠 쓰는 작업(DB INSERT와 Redis SET)은 언젠가 반쪽만 성공한다. 읽는 쪽에서 "없음"을 복구할 수 있으면 쓰는 쪽의 실패를 견딘다.
- `SET NX`는 "처음 쓴 값만 유효하다"를 원자적으로 보장한다. 여럿이 동시에 초기화하는 상황(캐시 채우기, 분산 락 획득)의 기본 도구다.
- SQLAlchemy `Row`는 튜플이다. 비어 있지 않으면 값과 상관없이 참이다. `scalar_*`에서 `one_or_none()`으로 바꿀 때 조건문도 같이 바꿔야 한다.
- SQL과 app 중 어디서 계산할지: 집계·필터, 하나의 기준(현재 시각), 원자성이 필요하면 DB에서 한다. 행 단위의 단순 계산은 어디서 해도 되고, 보통 도메인 규칙이 보이는 app 쪽을 고른다.
